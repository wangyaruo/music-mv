# 歌词准确性：为什么这是最容易翻车的一步

一首 MV 做得好不好，观众第一眼看的不是画面，是**字幕有没有错字**。
错一个字，整支片子的专业感就没了。而中文歌词恰恰是最容易出错的地方。

## 三个错误来源

### 1. ASR 对演唱中的中文歌词几乎不可用

真实案例。周杰伦《园游会》的正确歌词与某次 ASR 结果对比：

| 正确 | ASR 识别 |
|---|---|
| 我手中那张入场券 陪我数羊 | 我手中那张入场券被我收远不尔斯坦 |
| 摊位上一朵艳阳 我悄悄出现你身旁 | 摊位上一朵艳阳我悄悄住进你身旁 |
| 因为捞鱼的蠢游戏我们开始交谈 | 因为捞鱼的蠢游戏我们开始交单 |

原因很直接：演唱会把音节拉长、连读、加转音，还有和声叠在主人声上。
识别模型是按"说话"训练的，遇到"唱"就崩。

**ASR 仍然有用的部分**：段落边界。它给的 `0:32.000`、`0:43.850` 这类时间戳
通常是对的，因为那是整段的静音切分，与咬字无关。

### 2. 记忆会补全

人对歌词的记忆是"语义级"的，会自动把不通顺的地方替换成通顺的。
「陪我数羊」这种古怪的句子，记忆会自动改成「被我收得好好的」——一个更"合理"
但完全错误的版本。

**不要凭记忆写歌词。** 哪怕你确信自己听过一百遍。

### 3. 不同平台抄错同一个版本

歌词站之间存在大量互相复制。看起来"多个来源一致"也可能是同源错误。

## 校订流程

### 第一步：识别曲目

如果只给了音频，先确认是哪首歌：

```bash
# 抽一帧封面/片头看有没有曲名
ffmpeg -ss 20 -i input.mp4 -frames:v 1 frame.png
```

很多 MV 视频在开头 10-30 秒有曲名卡和词曲署名。

### 第二步：多源核对

至少查三个独立来源，关键词用**首句歌词 + 歌名**：

```
搜索: <歌手> <歌名> 歌词 <首句>
```

推荐来源（按可信度）：

1. 百度百科「歌曲歌词」段
2. 搜狗百科
3. 互动百科 / 维基
4. 正规歌词站（QQ音乐、网易云）

**判断方法**：三家以上完全一致 → 可信。有分歧 → 记下分歧点，
按多数派走，并在交付时主动说明。

### 第三步：逐字对音频念一遍

把核对后的歌词一行一行对着音频念。重点检查：

- 每句的**字数**
- 生僻搭配（"数羊"、"琉璃"、"透明感"这类不像口语的词，最容易抄错）
- 句尾押韵字（韵脚错了说明整句可能都错了）

### 第四步：把分歧写进交付说明

例：

> `气球在我手上 我牵着你瞎逛` 保留"瞎逛"——四个来源中三个作"瞎逛"，
> 百度百科作"瞎晃"，属流传版本分歧。

这比默默选一个更专业。

## 用段落边界做时间轴

歌词确定后，用 ASR 边界当"锚点"，把歌词切成组：

```json
{
  "grid_div": 4,
  "max_shift": 0.10,
  "groups": [
    {"t0": 32.00, "t1": 35.90, "lines": ["琥珀色黄昏像糖 在很美的远方"]},
    {"t0": 35.95, "t1": 43.40, "lines": ["你的脸没有化妆 我却疯狂爱上",
                                        "思念跟影子在傍晚一起被拉长"]}
  ]
}
```

组内每句的时长**按字数比例**分配，再吸附到 1/4 拍网格（位移上限 ±0.10s）。

为什么这样比"平均分配"好：中文歌词每句字数不同，平均分配会让长句显示时间不够。
为什么比"逐字强对齐"稳：没有可靠的强制对齐工具时，字数比例是很强的先验。

### 语速体检

`lyrics_timing.py` 会打印每句的 `s/字` 并标出偏离中位数 45% 以上的行。
同一首歌里语速应该大致均匀，出现 0.30 vs 0.38 这种大落差，通常说明
**某个组的边界估错了**——把两句并进了一组，或者把一句拆成了两组。

## 常见错误清单

- [ ] 主歌重复两遍，只改了一遍（第二遍还是错的）
- [ ] 副歌第一次和第二次歌词有细微差别，一律按一次处理
- [ ] 桥段的歌词整段漏掉
- [ ] 「的/地/得」按自己的习惯写，不是原词
- [ ] 全角/半角标点混用
- [ ] 句中的空格位置影响字幕分块，改歌词后要重新跑字幕脚本

## 用原片自带歌词做时间轴校准（最硬的证据）

如果用户给的是带滚动歌词的视频（KTV 版、歌词版 MV），那就是**免费的标准答案**。

### 取歌词区

```bash
# 原片 720x1280，歌词面板在下半部
ffmpeg -ss 31 -t 175 -i source.mp4 -vf "fps=2,crop=720:460:0:780" /tmp/lf/f_%04d.png
```

### OCR 读当前行

macOS 自带 Vision 框架，用 Swift 调，中文识别准确率够用：

```swift
// ocr.swift —— swiftc -O ocr.swift -o ocr
import Foundation
import Vision
import AppKit

for path in CommandLine.arguments.dropFirst() {
    guard let img = NSImage(contentsOfFile: path),
          let cg = img.cgImage(forProposedRect: nil, context: nil, hints: nil) else { continue }
    let req = VNRecognizeTextRequest()
    req.recognitionLanguages = ["zh-Hans"]
    req.recognitionLevel = .accurate
    req.usesLanguageCorrection = false          // 歌词不要纠错
    try? VNImageRequestHandler(cgImage: cg, options: [:]).perform([req])
    var items: [(CGFloat, String)] = []
    for obs in (req.results ?? []) {
        guard let c = obs.topCandidates(1).first else { continue }
        items.append((obs.boundingBox.midY, c.string))
    }
    items.sort { $0.0 > $1.0 }                   // 从上到下
    print("\(path)\t" + items.map { "\($0.0):\($0.1)" }.joined(separator: " ; "))
}
```

### 判读

歌词块是**提词器式滚动**：当前行固定在画面某一行的位置，整块逐步上移。

- 先丢掉顶部的「情书（音乐馆）」标题行
- 观察某一行的文本何时被新文本替换 → 那就是换行时刻
- 把两遍的换行时刻对齐，**同一句的差值必须是常数**

本案例实测：第一遍 44.5 / 48.0 / 52.0 / 56.0 / 60.0 / 63.5，
第二遍 139.0 / 143.0 / 146.5 / 150.5 / 154.5 / 158.0，差值恒为 94.5s。
而按字数比例分配出来的第二遍逐句滞后 1.2 → 2.8s，就是用户听到的"从 2:26 开始全乱"。

### 两个坑

- **不要试图找"高亮"**。这类视频的歌词是统一色，看着像有高亮往往是 JPEG 色偏
  或拼图色偏造成的错觉
- **不要用逐帧互相关追踪滚动量**。背景画面在动，会大量漏检和误检，
  聚类出来的"事件"一半是假的。用 OCR 读文本最稳
